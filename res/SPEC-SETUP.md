## Do

1. Create the project skeleton in `{{out_dir}}/` for the target: build manifest, source layout, a library crate or module for the behaviour and a thin entry point for the UI.
2. Install the toolchain the target needs inside the container (compiler, the libraries' development packages, anything tests need at runtime) and persist every install in `.devcontainer/Dockerfile` (see SKILL-base.md). Toolchain config outside the project (for example under `~/.cargo`) is fine.
3. Make the tests runnable from `{{out_dir}}/`. codehalter runs, in this order of preference: a `test` recipe in `{{out_dir}}/justfile`, else `cargo test`, `npm test` or `go test ./...` when the matching manifest is in `{{out_dir}}/`. If tests need anything special, such as a virtual display for GUI tests (`xvfb-run -a cargo test`) or an environment variable, write the `justfile` with a `test` recipe that provides it. For a compiled language, build tests with line tables only, not full debug info: nobody attaches a debugger in this container, backtraces keep file and line, and full debug info makes every test binary large and every link after a change slow (Rust: `[profile.dev] debug = "line-tables-only"` in `Cargo.toml`; C and C++: `-gline-tables-only` with clang or `-g1` with GCC in the debug flags; elsewhere the toolchain's equivalent). Where the language builds every test file into a program of its own (Rust's `tests/*.rs`, a CMake executable per test), make ONE test program with the test files as its modules (Rust: `tests/all.rs` declaring the shared test module and a `suite` module, one `mod` line per test file in `tests/suite/mod.rs`): every test program is another full link after each change, and one project grew 476 of them, 27 GB rebuilt after every edit. Tests that need a GUI toolkit bound to one thread (GTK) run on that thread through the toolkit's test helper (gtk4-rs: `#[gtk::test]`) and build the screen they check, instead of each starting the whole application, so they can share the one program. The `test` recipe runs the test files side by side, one process per test file and at most 16 at a time (fewer on a machine with fewer cores); for GUI tests each of those workers gets a virtual display of its own (`xvfb-run -a` around each worker, not around the whole run), so no two running tests share a display. One file after another took one project seven minutes for 530 files.
4. Check git: build output (for example `target/`) must be ignored, and sources, manifests and tests under `{{out_dir}}/` must NOT be. Verify with `git check-ignore -v <path>` and fix `.gitignore` where it is wrong.
5. Write one smoke test that passes. Put a shared test module next to it with a temporary directory per test, a fake server helper that binds port 0 and returns the port it got, and one wait helper every later test uses: it checks a condition, waits briefly, checks again, and fails after a deadline in wall-clock seconds with a message naming what never happened. Tests that wait for a timer, a thread, a child process or a file use it, never a fixed sleep or a fixed number of event-loop turns, so the suite holds up on a busy machine and when its test programs run in parallel.
6. Architecture, because every item will be checked by a test: keep behaviour (state, rules, data formats, flow steps) in plain testable code, and keep the UI layer thin, only rendering state and forwarding user actions. Logic inside a UI callback cannot be tested and will never count as done. The wire itself is tested too: every interactive widget gets a stable name (`set_widget_name`, from the spec's label), a test can build a screen, find a widget by name and fire its action (GTK: `emit_by_name`, `activate_action`), and the window's construction is a function tests can call, not code that only runs in `main`. Put one such widget test next to the smoke test so every later round has the pattern to copy.
7. If the target is a desktop GUI, make its screens visible from inside this container. There is no host display here, and there never will be: everything runs in the container.
   - Install a virtual display (`xvfb-run`), fonts and an icon theme. Without fonts and icons, screenshots come out with empty boxes where text and icons belong. Persist the installs in `.devcontainer/Dockerfile`.
   - Render without a GPU: set `GSK_RENDERER=cairo` for GTK 4 (the default GL renderer needs a graphics driver the container does not have).
   - Add a snapshot entry point to the app, in debug builds only: `--snapshot <screen> --project <fixture dir> --out <file.png>` builds the window in that screen's state from a fixture project, takes the picture when the screen is ready, renders the window with the toolkit's own API (GTK 4: a `gtk::WidgetPaintable` of the window, rendered with its renderer's `render_texture`, then `save_to_png`), and exits.
   - Ready is an event the app raises itself, never a guess: no timer, no sleep, no fixed number of frames, not the first frame. A guess catches the screen half set up in one run and settled in the next, and the picture check then judges whichever state it caught. Every setup step that can only run once its widget has a size (scrolling a list to its top, placing a divider, the window taking its size, data loaded in the background) registers as owed when it is scheduled and as done when it ran. The screen is ready at the first painted frame (GTK 4: the frame clock's `after-paint` signal) where no shown widget still owes a step. `--shot-on ready` (the default) takes the picture then; `--shot-on open:<widget-name>` also waits until the named widget, a menu or a popover, is shown.
   - At ready, record every shown widget's name and bounds, and take the picture one painted frame later only if none of them moved. If one moved, or the screen is not ready after a bound such as 600 frames, exit non-zero naming the widget that moved or the step still owed, and write no picture: a setup step that never registered shows up there, not as a picture that differs from run to run. Turn animations off (GTK 4: the `gtk-enable-animations` setting), and draw anything that changes by itself (a clock, a random value, the user's name) from fixed values in snapshot mode.
   - The entry point takes an optional `--do <widget-name>` that fires that widget's action before rendering, so a screen can be looked at after a click, not only at rest. A menu, popover or dialog is a surface of its own and the window's paintable does not contain it: for a screen with one open, render the window, then the open surface's own paintable, drawn onto the window's image where it opens, at its own size. Name the screens after the spec's image files (`03-window`, `05-cut`, ...), so each image in the spec has a reproducible counterpart.
   - Add a `snapshot` recipe to the `justfile` that runs it under `xvfb-run -a` with `GSK_RENDERER=cairo` and writes to `{{out_dir}}/shots/<screen>.png`. Each run works in a directory of its own at a fixed path per screen (for example `/tmp/<app>-shot/<screen>`), emptied and given a fresh copy of the fixture first, so no run sees what an earlier one left behind and no temporary path shows in the picture. Two runs of the same screen at once must not share that directory: hold a lock on it (`flock`).
   - Prove it: render one screen, even if it is still empty, twice, and compare the two files byte for byte (`cmp`): they must be identical. Then look at it with `screenshot path={{out_dir}}/shots/<screen>.png`. codehalter renders each screen twice before its picture check, and when the two differ the next round fixes the snapshot before anything else.
8. If the target is a web page or web app, make its pages visible the same way: add a `snapshot` recipe that starts the app (or serves the built files), opens `<screen>`'s page in a headless browser with Playwright (or a tool like it that can wait for a condition), writes `{{out_dir}}/shots/<screen>.png` with `page.screenshot`, and stops the app again. Ready is the page's own event here too: the app sets an attribute (for example `data-ready` on `<body>`) once its data has loaded and the page is laid out, and the recipe waits for that attribute and for `document.fonts.ready`, never for a fixed timeout or "network idle". `firefox --headless --screenshot` takes the picture at load and cannot wait, so it only fits a page that is complete without scripts. Turn animations and transitions off (Playwright's `reducedMotion: 'reduce'` and a stylesheet that sets `animation: none; transition: none`), give the page fixed data from a fixture, name the screens after the spec's image files, as above, and prove it the same way, twice with `cmp`.

codehalter checks it itself afterwards: a test command is found for `{{out_dir}}/`, at least one test source exists there, and the test command passes.
