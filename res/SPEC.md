## Read the spec before you plan

The section at the end of this prompt is where the item starts, rarely all of it. A screen's picture shows parts other chapters specify, a table in another file gives its labels and defaults, and an answer in `QUESTIONS.md` may have changed it. Rounds that built from the section alone drew a second copy of a readout the window's bottom bar already shows, laid a menu out as a row of ticks because only the inventory said "menu", printed a title where the render does not print it, and left out a switch named once in another chapter. So in the PLANNING phase, before the plan:

1. Collect every place that specifies this item: its section; the sections it links (appended below it); the chapter's screen description, its first section with the numbered badges; any table the chapter calls normative (an inventory of labels, options, defaults, tooltips and sizes); the standing-rules files named above; and the answers to this item's questions. Open with the shell the ones not included below. A normative table or an answer is spec as much as the section is.
2. If this item shows a screen, list every part its picture shows, and beside each part the sentence that specifies it and the file that sentence is in. For a part with no sentence in what you collected, search the whole spec for its name before deciding the spec is silent: it is usually another chapter's (the window's frame belongs to the shell, a gutter to the page that owns the tracks). A part the text says is gone or replaced is not built, since the picture may be of a prototype. Build to the sentences, and take from the picture what they leave open: arrangement, order, which control is a menu and which a row of ticks.
3. Where two places disagree, the more specific one decides: an answer over the section, the section over the picture, a table the chapter calls normative over a summary sentence that only names the thing. When a section names a thing but not where it is (a readout, a switch), find where the spec puts it: a thing has one place, and you do not draw a second copy of something the window or another page already shows.
4. For every number, find what it measures (pixels of the window, a fraction of a picture, seconds of the cut) and which code already uses it. Where the program already computes what the screen shows (the box the render prints a title into, the count the bottom bar reads), draw from that same code: a second copy with its own numbers drifts from the first.
5. Name the facts you will test, each beside the sentence it comes from. A test asserts the number the spec states, not the one your code happens to produce.

Put the list from 2 (part, sentence, file) and the facts from 5 into the plan's first subtask, so the execution builds against them and your look at the render can be checked against the same list.

## How to work

- Read what already exists in `{{out_dir}}/` before writing. Earlier rounds implemented other items; extend and reuse their code, do not write a second version of something that is there.
- Implement exactly what the spec text below says. Every numbered step (S1, S2, ...) and every branch should be exercised by a test; name step tests `{{token}}_s1_...`, `{{token}}_s2_...`.
- Parameters (`P.*`) and tools (`tool:*`) this text cites are items of their own, listed with their rows. Where your code uses one, name a test that checks it after the row's token; the row is then done without a round of its own. The rows cited here, with their tokens: {{row_tokens}}.
- Keep behaviour in plain, testable code (state, rules, data formats, flow steps) and the UI layer thin: it renders state and forwards user actions. A step whose logic lives inside a UI callback cannot be tested, so it can never count as done. Give every interactive widget you add a stable name (`set_widget_name`, from the spec's label, for example `add-source`), so tests and the snapshot entry point can find it.
- Write only the tests this item needs: one for each fact its text states (a step, a branch, a number, a message), each checking only this item's outcome, through the item's own entry point. A fact another item's section states is that item's to test, so do not assert it here: where the run bar sits, how the window is split, what another flow returns. Before adding a test, look for one that already checks the same fact and extend it instead of writing a second. How a screen is arranged (what sits where, how a page is split) is judged by codehalter's own look at your render beside the spec's picture; assert a pixel number only where the spec text states that number. Before the round counts, codehalter reviews the tests it wrote: a test that checks another item's fact, repeats another test, waits a guessed amount, or uses a fixed path, port or display comes back to you to narrow, merge or remove.
- Tests are deterministic on any machine and under any load; the suite may run in parallel with other test programs on a busy machine. A test does not call a live server (it uses the project's loopback fakes) and does not read a status line that other parts of the program also write; it asserts the state its action changes. A test that fails at random fails other rounds, which are not at fault.
- A new test joins the project's one test program; it is not a program of its own. Where the language builds every test file into its own program (Rust's `tests/*.rs`): put the file in `tests/suite/` with its `mod` line in `tests/suite/mod.rs` (create `tests/all.rs` with the shared test module and `mod suite;` if it is not there yet), never a new `[[test]]` target. A widget test runs on the GUI toolkit's one thread through its test helper (gtk4-rs: `#[gtk::test]`) and builds the screen it checks, rather than starting the application.
- A test never waits a guessed amount: no fixed sleep, no fixed number of event-loop turns, no "until nothing is pending". On a busy machine the work is not done yet when the guess runs out. Whatever happens later (a timer, a background thread, a child process, a file another part writes) is awaited as a condition: check it, wait briefly, check again, and fail only after a generous deadline in wall-clock seconds (10 s, say), with a message that names what never happened. Use the one wait helper in the shared test module, or add it there; do not write another. For a file another part writes, watch it with the platform's file watcher (inotify, the `notify` crate, `fsnotify`, `watchdog`) or wait for it through the helper. To make one file newer than another, set its modification time; never sleep between the two writes. A test that drives a fake clock must also make every timer the code relies on read that clock; otherwise it still waits on real time. Each test is isolated, so test files can run side by side: it writes only into its own temporary directory (the platform's temp-dir call, which follows `$TMPDIR`), never a fixed path inside or outside the project such as `/tmp/take.wav` or `fixtures/out.mp4`; a fake server binds port 0 and hands the port it got to the code under test, never a fixed port; a GUI test uses the display it is given (`$DISPLAY`), never a fixed display number. codehalter runs the test command with a fresh `$TMPDIR` and reports anything the run wrote outside it.
- Where the spec is silent, decide in its spirit and in line with the target, and write what you decided in a code comment. Where the spec contradicts itself or the target, ask instead of guessing. A layout, a label or an order the spec states elsewhere (the chapter's screen description, its image) is not a question: follow it, even outside this item's own section. Code that does not match the spec yet is work to do, not a contradiction to ask about. A question goes into the spec's `QUESTIONS.md` for the user, who answers it there without opening the code, so it must stand on its own: call `submit_plan` with clear=false, no subtasks, `question` (one sentence naming what the user must decide), `spec_quote` (the spec text that comes closest to deciding it, copied exactly from a spec file; codehalter checks it is there) and `options` (2 or 3 ways to decide it, your pick first, each a short `choice` and an `example` of what the user would see or the program would do with it, such as a label, a layout, a value or a line of a file).
- If you changed a UI source file, look at the result before you finish, whether or not the spec has a picture of it: render the screen with the `snapshot` recipe and look at the image with `screenshot`. Is every widget the text names on it, in the order it says; is nothing empty, overlapping, cut off or unlabeled? If this item's text shows a screen (the spec images listed under "Screens" at the end), look at the spec's image too and compare: widgets, their order, labels and tooltips must match; exact pixels, colours and spacing need not. Everything runs inside this container, headless: never ask for a display. A UI change without a look does not count as done.
- Run the suite once, last, after your final edit, as its own command: `cd {{out_dir}} && {{test_cmd}}` (a redirection to a file is fine). A green run then counts as the check and codehalter does not run the suite a second time. Do not wrap it in a subshell or append `echo exit=$?`: the exit code is then the echo's and the run does not count.
- Stay on this item: build only what it specifies. The sections linked below are there to be read (see "Read the spec before you plan"), not built; their rounds will come.
- Format only the files you changed (`rustfmt <file>`, `gofmt -w <file>`, `prettier --write <file>`), never the whole project (`cargo fmt`, `go fmt ./...`, `prettier --write .`): one round reformatted 859 files, its own change was lost among them, and every line of them was then checked as if the round had written it.
